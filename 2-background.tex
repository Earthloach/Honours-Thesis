\chapter{Background}\label{chap:background}

\section{Guarded Recursion and the Later Modality}
\label{sec:bg-guarded}

Many programs are not intended to terminate. Cloud servers and
reactive programs run continually, consuming and producing potentially
infinite amount of data. For such programs the appropriate correctness
criterion is not termination but \emph{productivity}: 
the program keeps producing output as it operates.

\subsection{Syntactic Productivity Checks}
The traditional approach of ensuring productivity is \emph{syntactic check} \citep{coquand93}, where it requires every recursive call
appear directly beneath a data constructor. Consider the following
stream programs, where \texttt{::} is the
stream constructor:

\begin{lstlisting}[style=hs]
ones = 1 :: ones
nats = 0 :: map (+1) nats
bad  = bad
\end{lstlisting}

\noindent
The check accepts \texttt{ones} and rejects \texttt{bad}, which is never
able to produce a single element. However, it also rejects \texttt{nats}, which is indeed productive, and it generates
$0, 1, 2, \ldots$. Since its recursive call is guarded by a function \texttt{map}
rather than directly by a constructor, the checker cannot see that \texttt{map}
produces one output element for each input. A more flexible approach is guarded recursion, which 
offers productivity guarantee through types \cite{nakanoModalityRecursion2000}.

\subsection{The Later Modality}

Guarded recursion introduces a type modality called ``later'', written
$\triangleright$. The later modality employs a notion of \emph{logical time}, 
data of type $\tau$ is considered available now, while data of type $\triangleright \tau$ becomes accessible one step later. 
Productivity is then enforced by a single rule: every self-reference must
be guarded by a $\triangleright$. For data types, this means a recursive
occurrence of the type must appear beneath the later modality. A guarded stream type is 
therefore defined as the follow:
\[ \tstr{\tau} \triangleq \tau \times \triangleright \tstr{\tau}\]

The head of a stream is accessible now while the tail is only available later.
For programs, this means that within its own definition, a recursive
reference is only available later: it has type $\triangleright\tau$ rather
than $\tau$. For instance, the stream programs from the previous section
are typed as follows:\footnote{For readability, we leave the delays implicit
here. In practice, calculi based on guarded recursion provide explicit term
constructs for introducing and applying delayed values.}

\begin{lstlisting}[style=hs]
map : (a -> b) -> Stream a -> Stream b
map f (x :: xs) = f x :: map f xs

ones : Stream Int
ones = 1 :: ones

nats : Stream Int
nats = 0 :: map (+1) nats

bad  = bad
\end{lstlisting}

\noindent
In \texttt{ones}, the recursive reference has type
$\triangleright\tstr{\mathsf{Int}}$, which is exactly the type required for
the tail. In \texttt{map}, both the tail \texttt{xs} and the recursive call
are available only later, so the recursive call yields a value that is typed $\triangleright\tstr{a}$. Crucially,
\texttt{nats} is now accepted: applying \texttt{map (+1)} to the delayed
recursive reference produces a delayed stream, which fits the type. In contrast,
\texttt{bad} is still rejected: its definition requires a stream now, but its
recursive reference is only available later.

Guarded recursion has since been developed in a range of calculi and type
theories to reason about infinite data \citep{atkeyProductiveCoprogrammingGuarded2013a, mogelberg14,bahrClocksAreTicking2017}, which 
In this thesis, we follow the guarded $\lambda$-calculus~\citep{cloustonGuardedLambdaCalculusProgramming2017a},
which extends the simply typed $\lambda$-calculus with the later modality
and guarded recursive types.

Another major application of guarded recursion is functional reactive programming ~\citep{elliottH97}, 
where programs describe values that change over time and react to events continuously.
Guarded recursion not only guarantees productivity to such programs but also helps to rule out undesired properties like space
leaks ~\citep{krishnaswamiBH12, bahrSimplyRaTTFitchstyle2019a}. Nontheless, it says nothing about the computational work
performed at each step: a productive stream may do ever more work for
each successive element. The following
section introduces the tool we use to model costs.

\section{Type-Based Cost Analysis}
\label{sec:bg-cost}
Static cost analysis aims to bound the resources a program consumes, such
as its number of evaluation steps, before the program is run. Type systems offer a
compositional way to achieve this: the type of a program states an upper bound on
its cost, and this bound is checked together with the rest of the program.

A natural way to account for cost in types is to treat it as a
\emph{computational effect}: running a program performs additional effects rather than just computing a value, 
such as printing the output and producing costs. In particular, \citet{moggi91} showed that a wide
range of effects can be modelled uniformly using monads: the monad
type $\tmonad{}{\tau}$ describes computations that may perform effects and eventually
produce a value of type $\tau$.

Our work specifically builds on
$\lambda$-amor~\citep{rajaniUnifyingTypetheoryHigherorder2021a}, a type
system for cost analysis that follows this monadic discipline. To record how
much cost a computation incurs, $\lambda$-amor uses a \emph{graded}
monad~\citep{katsumata14}, a monad whose type carries an additional
annotation. A type $\tmonad{I}{\tau}$ describes a computation that
produces a value of type $\tau$ with a cost of at most $I$, where $I$ is a \emph{nonnegative} real number. 
Following the standard treatment of monads, the graded cost monad has the following basic operations:
\[
  \ret e : \tau \to \tmonad{0}{\tau}
  \qquad\qquad
  \bind{x}{e_1}{e_2} : \tmonad{I}{\tau_1} \to \tmonad{J}{\tau_2} \tmonad{I + J}{\tau_2}
\]
The operation $\mathsf{ret}$ lifts an ordinary program $e$ into an effectful computation that returns
its value without incurring any cost. This gives the flexibility to transform normal programs to monads, allowing them to interact with other monadic computations.
By the $\mathsf{bind}$ operation, a computation $e_1$ of type $\tmonad{I}{\tau}$ can be sequenced into a continuation $e_2$ of type $\tmonad{J}{\tau}$ which may use the result of $e_1$ as $x$, and their 
costs will be summed as $I+J$.
For example, consider the program defined below:
\begin{lstlisting}[style=hs]
doWork1 : M 10 a
doWork2 : M 20 b

doBoth : M 30 b 
doBoth = bind x = doWork1 in doWork2
\end{lstlisting}
he program \texttt{doBoth} first runs \texttt{doWork1} and then \texttt{doWork2}, so its cost is the sum $10 + 20 = 30$ of the two.

The cost bounds discussed so far are \emph{worst-case} bounds: each operation is
charged for its most expensive possible execution. For operations whose cost can
vary largely, this can be overly pessimistic. Beyond
worst-case bounds, $\lambda$-amor can also analyse amortised costs, 
which we introduce in the next section.

\section{Amortised Analysis}
Many type-based cost analysis frameworks like $\lambda$-amor support
\emph{amortised} analysis \citep{hofmannJ03, JostHLH10, Danielsson08}.
In this section, we give a brief introduction to amortised analysis, as it is part of our development in this thesis.

\emph{Amortised analysis}~\citep{tarjan85} bounds the total cost of a
\emph{sequence} of operations rather than the cost of each individual operation. 
The cost of rare expensive operations is thereby spread over the
cheap ones, which often yields much tighter bounds than worst-case analysis.

A standard technique for amortised analysis is the \emph{potential
method}. The method associates data structures with a \emph{potential function} $\Phi$, which assigns a
non-negative number to each state of the data structure The \emph{amortised cost}
$a$ of an operation that takes the state from $s$ to $s'$ with actual cost
$c$ is required to satisfy:
\[
  c + \Phi(s') \;\le\; a + \Phi(s).
\]
In particular, the amortised cost together with the potential before the
operation must cover both the actual cost and the potential left
afterwards.
Summing over a sequence of $m$ operations from state $s_0$ to $s_m$, the
potentials in between cancel, and we get
\[
  \sum_{i=1}^{m} c_i \;\le\; \sum_{i=1}^{m} a_i + \Phi(s_0) - \Phi(s_m)
  \;\le\; \sum_{i=1}^{m} a_i + \Phi(s_0).
\]
Thus, if the data structure starts with zero potential, the total actual cost is
bounded by the total amortised cost.

A classic example is a binary counter, represented as a list of bits with
the least significant bit at the front. Incrementing the counter flips trailing
ones to zeros until it reaches a zero, and updates it to one:

\begin{lstlisting}[style=hs]
data Bit = Zero | One

inc :: [Bit] -> [Bit]
inc []          = [One]
inc (Zero : bs) = One : bs
inc (One : bs)  = Zero : inc bs
\end{lstlisting}

\noindent
Suppose incrementing one bit costs one unit. In the worst case, a single
increment of a counter with $k$ bits flips all of them, which costs $k + 1$.
For instance, incrementing \texttt{[One, One, One]} yields
\texttt{[Zero, Zero, Zero, One]} with a cost of $4$. However, such expensive
increments are rare: after one occurs, the low bits are all zeros, and many
cheap increments must follow before an expensive one can happen again.

The potential method makes this precise. Let $\Phi$ be the number of
\texttt{One} bits in the counter. Consider an increment that flips $k$
trailing ones to zeros and the ending zero to a
one. Its actual cost is $k + 1$. Its potential decreases by $k$ and
increases by $1$, so
\[
  c + \Phi(s') = (k + 1) + (\Phi(s) - k + 1) = 2 + \Phi(s).
\]
Every increment therefore has amortised cost $2$, regardless of $k$:
each \texttt{One} bit stores the unit of potential needed to flip it back to
\texttt{Zero}. Starting from the empty counter, $m$ increments cost at most
$2m$ in total, whereas worst-case analysis only gives a bound that grows
with the size of the counter.
