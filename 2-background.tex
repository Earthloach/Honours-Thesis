\chapter{Background}\label{chap:background}

\section{Guarded Recursion and the Later Modality}
\label{sec:bg-guarded}

As discussed in Chapter~\ref{chap:Introduction}, the appropriate property for non-terminating programs is 
\emph{productivity}. This section reviews two ways of ensuring productivity, first by a syntactic
check and then through type systems.

\subsection{Syntactic Productivity Check}
The traditional approach to guaranteeing productivity is a \emph{syntactic check} \citep{coquand93}, which requires every recursive call to
appear directly beneath a data constructor. Consider the following
stream programs, where \texttt{::} is the
stream constructor:

\begin{lstlisting}[style=hs]
ones = 1 :: ones
nats = 0 :: map (+1) nats
bad  = bad
\end{lstlisting}

\noindent
The check accepts \texttt{ones} and rejects \texttt{bad}, which is never
able to produce a single element. However, it also rejects \texttt{nats}, which is indeed productive, and it generates
$0, 1, 2, \ldots$. Since its recursive call is guarded by a function \texttt{map}
rather than directly by a constructor, the syntactic checker cannot see that \texttt{map}
produces one output element for each input. A more flexible approach is guarded recursion, which 
ensures productivity using types \citep{nakanoModalityRecursion2000}.

\subsection{The Later Modality}

Guarded recursion introduces a type modality called ``later'', written
$\triangleright$. The later modality employs a notion of \emph{discrete logical time}: 
data of type $\tau$ is considered available now, while data of type $\triangleright \tau$ becomes accessible one step later. 
Productivity is then enforced by a single rule: every self-reference must
be guarded by a $\triangleright$. For data types, this means a recursive
occurrence of the type must appear beneath the later modality. For any type $\tau$, a guarded stream type is 
therefore defined as follows:
\[ \tstr{\tau} \triangleq \tau \times \triangleright \tstr{\tau}\]

The head of a stream is accessible now while the tail is delayed by the modality.
For programs, this means that within its own definition, a recursive
reference is guarded: it has type $\triangleright\tau$ rather
than $\tau$. For instance, the stream programs from the previous section
are typed as follows:\footnote{For readability, we leave constructs of the later modality implicit in the example programs. In practice, calculi often provide explicit syntax and operations
for the later type.}

\begin{lstlisting}[style=hs]
map : (a -> b) -> Stream a -> Stream b
map f (x :: xs) = f x :: map f xs

tail : Later Stream a 
tail (x :: xs) = xs

ones : Stream Int
ones = 1 :: ones

nats : Stream Int
nats = 0 :: map (+1) nats

\end{lstlisting}

\noindent
In \texttt{ones}, the inner self-reference has type
$\triangleright\tstr{\mathsf{Int}}$, which is exactly the type required to construct a guarded stream.
This is also reflected by the tail function, which gives a ``Later'' stream.
In \texttt{map}, both the tail \texttt{xs} and the recursive call
are guarded, so the recursive call yields a value that is typed $\triangleright\tstr{a}$. Crucially,
\texttt{nats} is now accepted: applying \texttt{map (+1)} to the guarded
recursive reference produces a guarded stream, which fits the type. In contrast,
\texttt{bad} will still be rejected: its definition requires a stream now, but its
recursive reference is guarded.

Guarded recursion has since been developed in a range of calculi and type
theories to reason about infinite computations \citep{atkeyProductiveCoprogrammingGuarded2013a, mogelberg14,bahrClocksAreTicking2017}.
In this thesis, we follow the guarded $\lambda$-calculus~\citep{cloustonGuardedLambdaCalculusProgramming2017a}, 
which is an extension of the simply typed $\lambda$-calculus with the later modality, and supports productive definitions of infinite data structures.

\section{Type-Based Cost Analysis}
\label{sec:bg-cost}
Static cost analysis aims to bound the resources a program consumes, such
as its number of evaluation steps, before the program is run. Type systems offer a
compositional way to achieve this: the type of a program states an upper bound on
its cost, and this bound is checked together with the rest of the program.

A natural way to account for cost in types is to treat it as a
\emph{computational effect}: running a program performs additional effects rather than just computing a value, 
such as printing the output and producing costs. In particular, \citet{moggi91} showed that a wide
range of effects can be modelled uniformly using monads: the monad
type $\tmonad{}{\tau}$ describes computations that may perform effects and eventually
output a value of type $\tau$.

Our work specifically builds on
$\lambda$-amor~\citep{rajaniUnifyingTypetheoryHigherorder2021a}, a type
system for cost analysis that follows this monadic discipline. To record how
much cost a computation incurs, $\lambda$-amor uses a \emph{graded}
monad~\citep{katsumata14}, a monad whose type carries an additional
annotation. A type $\tmonad{I}{\tau}$ describes a monadic computation, but with an extra grade $I$ representing an upper bound on the cost of executing it, where $I$ is a \emph{nonnegative} real number. 
Following the standard treatment of monads, the graded cost monad has the following basic operations:
\[
  \ret e : \tau \to \tmonad{0}{\tau}
  \qquad\qquad
  \bind{x}{e_1}{e_2} : \tmonad{I}{\tau_1} \to \tmonad{J}{\tau_2} \to \tmonad{I + J}{\tau_2}
\]
The operation $\mathsf{ret}$ lifts an ordinary program $e$ into an effectful computation that returns
its value without incurring any cost. This gives the flexibility to transform normal programs into monads, allowing them to interact with other monadic computations.
By the $\mathsf{bind}$ operation, a computation $e_1$ of type $\tmonad{I}{\tau}$ can be sequenced into a continuation $e_2$ of type $\tmonad{J}{\tau}$, where $e_2$ may use the result of $e_1$ as $x$, and their 
costs will be summed as $I+J$ to account for the work done by both.
For example, consider the program defined below:
\begin{lstlisting}[style=hs]
doWork1 : M 10 a
doWork2 : M 20 b

doBoth : M 30 b 
doBoth = bind x = doWork1 in doWork2
\end{lstlisting}
The program \texttt{doBoth} first runs \texttt{doWork1} and then \texttt{doWork2}, so its cost is the sum $10 + 20 = 30$ of the two.

The cost bounds discussed so far are \emph{worst-case} bounds: each operation is
charged for its most expensive possible execution. For operations whose cost can
vary greatly, this can be overly pessimistic. Beyond
worst-case bounds, $\lambda$-amor can also analyse amortised costs, 
which we introduce in the next section.

\section{Amortised Analysis}
\label{sec:bg-amortised}
Many type-based cost analysis frameworks support
amortised cost bounds \citep{hofmannJ03, JostHLH10, Danielsson08}.
In this section, we give a brief introduction to amortised analysis, as it is part of our development in this thesis.

\emph{Amortised analysis}~\citep{tarjan85} bounds the total cost of a
\emph{sequence} of operations rather than the cost of each operation. 
The cost of rare expensive operations is thereby spread over the
cheap ones, which often yields much tighter bounds than worst-case analysis.

A standard technique for amortised analysis is the \emph{potential
method}. The method associates data structures with a \emph{potential function} $\Phi$, which assigns a
nonnegative number to states of the data structure. The \emph{amortised cost}
$a$ of an operation that takes the state from $s_n$ to $s_{n+1}$ with actual cost
$c$ is required to satisfy:
\[
  c + \Phi(s_{n+1}) \;\le\; a + \Phi(s_n).
\]
In particular, the amortised cost together with the potential before the
operation must cover both the actual cost and the potential left afterwards.
Summing over a sequence of $m$ operations from state $s_0$ to $s_m$, the
potentials in between cancel, and we get
\[
  \sum_{i=1}^{m} c_i \;\le\; \sum_{i=1}^{m} a_i + \Phi(s_0) - \Phi(s_m)
  \;\le\; \sum_{i=1}^{m} a_i + \Phi(s_0).
\]
Thus, if the data structure starts with zero potential, the total actual cost is
bounded by the total amortised cost. In particular, we usually choose potential functions to achieve the effect that an expensive operation
results in a substantial decrease in the potential between two states. For example, if we choose a potential function such that $\Phi(s_n)$ is very large while 
$\Phi(s_{n+1})$ is small, then $a$ becomes relatively small compared to $c$.

A classic example of amortised analysis is a binary counter, represented as a list of bits with
the least significant bit at the front. Incrementing the counter flips trailing
ones to zeros until it reaches a zero, and updates it to one:

\begin{lstlisting}[style=hs]
inc :: List Bit -> List Bit
inc []          = [One]
inc (Zero : bs) = One : bs
inc (One : bs)  = Zero : inc bs
\end{lstlisting}

\noindent
A bit is either \texttt{One} or \texttt{Zero}.
Suppose incrementing one bit costs one unit. In the worst case, where the elements inside are all ones, a single
increment of the counter with $k$ bits flips all of them, which costs $k + 1$.
For instance, incrementing \texttt{[One, One, One]} yields
\texttt{[Zero, Zero, Zero, One]} with a cost of $4$. However, such expensive
increments are rare: after this increment occurs, the low bits are all zeros, and many
cheap increments must follow before an expensive one can happen again.

The conventional approach is to let $\Phi$ be the number of
\texttt{One} bits in the counter. Consider an increment that flips $k$
trailing ones to zeros and the first zero to a
one. Its actual cost is $k + 1$. Its potential decreases by $k$ and
increases by $1$, and we get
\[
  c + \Phi(s_{n+1}) = (k + 1) + (\Phi(s) -  k + 1) = 2 + \Phi(s_{n}).
\]
Every increment therefore has amortised cost $2$, regardless of $k$. 
Starting from the empty counter, $m$ increments cost at most
$2m$ in total, while worst-case analysis only gives a bound that grows
with the size of the counter.

Another point of view is that 
each \texttt{One} bit stores one unit of potential locally to pay for the cost of flipping it back to
the \texttt{Zero} bit. This is the approach adopted by existing systems such as $\lambda$-amor~\citep{rajaniUnifyingTypetheoryHigherorder2021a}, where types carry potential to offset costs.
